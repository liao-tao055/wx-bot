# 个人微信推送：云端重试直到发送成功

MCP 0.4.0 按绑定本人在会话中的明确授权，为新提交的任务结果启用服务端持续重试。
不再把“每次失败都确认一次”作为新任务的默认流程。插件、Worker、微信绑定和收件人保持原样。

## 当前规则

- 新任务首次提交时保留原 delivery_id、内容指纹、收件人和附件原始字节。
- 首次发送立即尝试。失败后文件仍在 Durable Object 中，不依赖原对话继续运行或手机存文件。
- 后台轮询周期内的重试循环执行到期任务；对象重启后从持久化任务继续。
- 可明确识别的拒绝至少等待 30 秒；网络超时等结果不明的失败至少等待 120 秒。
  随失败次数增加，间隔延长到最多 15 分钟；没有固定重试次数上限。
- 正在执行的请求有 20 分钟租约，租约期间不会并发补发。异常中断后到期才接管。
- 保持每段消息的 client_id 稳定，减少上游重复消息；这不等于承诺严格只送达一次。
- 记录为 sent 后停止重试并清理保存的文件块。同编号和不同内容仍然拒绝。
- 缺少会话或登录失效时保留任务等待恢复。新入站消息会唤醒等待会话的任务；
  登录过期仍需本人扫码，程序不会假造新会话或替换收件人。

## 旧记录

升级前的 uncertain/sending 不会因版本更新被自动解锁。旧 uncertain 由本人确认未收到并
授权后，沿用旧确认接口和原文件提交一次，即进入持续重试；之后不再每次确认。
sent 和正在执行的旧记录不解锁。本次原测试 PDF 已是 sent，不再重复发送。

## 调用方

queued=true 表示已保留并等待后台重试，不能声称已经送达。调用方查
wechat_delivery_status 的 retry_mode、retry_attempts、next_retry_at，不能另换编号或重复上传。
wechat_status 的 retry_policy.mode 应为 until_sent，retry_queue 显示待处理数量。
微信接口确认成功或交付状态 sent 才报告成功。

附件按 64 KiB 分块保存、每批最多 64 个键，符合存储 API 的批量和大小限制。
https://developers.cloudflare.com/durable-objects/platform/limits/

验证包括：文件分块恢复、指数退避、上下文唤醒、并发互斥、旧记录首次授权、
成功终止、过期租约接管、迟到失败不能覆盖 sent、原始文件校验和稳定消息标识。
本地使用 Node 适配执行 Bun 测试；原生 Bun 与 TypeScript 全量检查未在当前执行环境运行。
